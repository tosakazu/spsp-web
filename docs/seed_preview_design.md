>   名前を復元できない参加者はステータス行に uid を列挙する (「uid:xxxx」表示は廃止)。

シード作成/アップロードページから「作成中のシードで組んだトーナメント」を
ブラケットUIでプレビューする機能。プレビューは **リンク発行型**: 状態を丸ごと
URL 化した別ページで、URL を共有すれば誰でも同じ画面が見られる。

ユーザー決定事項:
- フェーズ区切りは **発行時に初期値を指定でき、プレビューページ側でも変更可能** (両方)。
- 大規模大会 (URL が Discord 等に貼れない場合) は **作業状況CSVのファイル import** で代替。
- 海外勢は **国名まで表示** (`players/<uid>.json` の `country_ja` / `country`。
  プレイヤーページと同じデータ経路。URL やクエリの変更は不要)。
- v1 は **勝者側のみ**。敗者側は構造・トグル (`lb`) を最初から想定しておき後続で追加。

## 2. URL 設計

```
https://spsp.games/bracket/#v=1&ph=0&pool=A3&lb=0&wd=0&d=<blob>
```

- **フラグメント (#) に載せる**: サーバーへ送信されないため Apache のリクエスト行制限
  (~8KB) を回避。ブラウザは数百KBまで実用上問題ない。
- `d` = ペイロード JSON → **deflate-raw → base64url**。ブラウザ標準の
  `CompressionStream('deflate-raw')` を使用 (外部ライブラリなし)。
  Node テストでは `zlib.deflateRawSync` が同一バイト列を生成するので往復検証できる。
- 表示状態 (`ph` フェーズ index / `pool` プール表示名 / `lb` 敗者側 / `wd` 平日込み) は
  blob の外の短いパラメータ。UI 操作のたび `history.replaceState` で更新し、
  **アドレスバーの URL = 常に完全な共有リンク**。
- blob を変える操作 (フェーズ構成の編集・CSV import) も同様に URL を書き換える。

実測サイズ (uid列 + 未登録者名のみ、deflate level 9 → base64url):
512人 ≈ 2,800字 / 2,048人 ≈ 11,000字 / 3,000人 ≈ 16,500字。
**名前列は持たない** (uid から `players/<uid>.json` の `display` で復元。2026-08-13 ユーザー指示)。
uid 列の varint バイナリ詰めも実測したが deflate 後の差が ~13% (3,000人で 16.5K→14.4K字) しか
なく、複雑さに見合わないため JSON+deflate を採用。
ブラウザ・メールは全域OK、LINE は ~1,800人までOK、Discord (2,000字) はほぼ不可 → CSV import で代替。

### ペイロード (v:1)

```js
{
  v: 1,
  ev: "篝火#15 / ultimate-singles",   // 表示用イベント名 (自由文字列)
  src: 'spsp' | 'csv',                 // 発行元モード (表示の注記用)
  phases: [                            // 先頭 = 予選。最終フェーズは pools:1
    { name: '予選', pools: 128, adv: 2 },
    { name: 'Top 256', pools: 8, adv: 4 },
    { name: 'Top 32', pools: 1, adv: 0 },
  ],
  wv: [0,0,...,1,1],                   // 予選プール index → ウェーブ index (長さ = phases[0].pools)。
                                       // ウェーブ情報なしなら省略
  uids:  [1000070, null, ...],         // シード順。SPSP 未登録者は null
  names: { "0": "あcola", "1": "NoDBPlayer", ... },   // index → 表示名
}
```

- **プール数は `phases[*].pools` が正** (予選 = `phases[0].pools`。発行時に `so-pools` から埋める)。
  `wv` は長さ = `phases[0].pools` であることを復号時に検証する (不一致は fail-loud)。
- シード番号 = 配列 index + 1。bye は暗黙 (プール内人数 < 2^k)。
- シード固定・手動調整等は発行時点の並びに反映済みなので **並び以外は持たない**。
- **`names` は原則 全参加者分を載せる** (2026-08-13 変更)。当初は「登録者は uid から
  復元できるので不要」としていたが、`players/<uid>.json` は上位帯で 1 人 0.5〜1.7MB あり、
  64 人プールでは数十 MB になる。取得が遅い/失敗する回線では**名前が一切出ない**という
  壊れ方をしたため、名前は URL 側に持たせて取得結果に依存させない。
  - 発行時に URL が `BRACKET_URL_BUDGET` (9,500字) を超える規模では、DB 未登録者の名前だけに
    落とす (その規模ならプール当たりの人数が小さく、プレビュー側の取得も軽い)。落とした場合は
    発行時のメッセージに明示する。
  - `players/<uid>.json` は**居住地・直近対戦・プロフィール用に後追いで取得**する。
    描画はこれを待たない (先に名前入りで描き、取得後にバッジを足して再描画)。
  - 名前がどうしても出せない参加者は、理由 (取得失敗 HTTP xxx / DB になし / 表示名なし) と
    シード番号をステータス行に出す。取得失敗は「🔄 再取得」で再試行できる
    (`__error` は再取得対象、404 は確定なので対象外)。

### データ版 (2026-08)

「相手と同じデータを見ているか」を突き合わせるための短いハッシュ。プレビューページの
ヘッダと、シードページの発行時メッセージの両方に同じ値を出す。

```
S.payloadVersion(payload) → 'ABCD-EFGH'   (Crockford base32 で 40bit)
```

**版に含めるもの** = ブラケットの中身を決める要素だけ:
`ev` (大会名) / `uids` (シード順) / `phases[]` の `name,pools,adv,lb` / `wv` / `prog`

**含めないもの**:

| 除外するもの | 理由 |
|---|---|
| フラグメントの `ph` / `pool` / `wd` / `lb` / `hi` | 見る側の状態。どのプールを開いているかで版が変わったら突き合わせに使えない |
| `names` | 表示専用。URL が長くなる規模では DB 登録者ぶんを落とすので、同じブラケットでも URL の作り方で中身が変わる |
| `src` | 発行元がシードページか CSV かの別。同じブラケットなら同じ版であるべき |
| `d=` の blob 自体 | deflate の出力は実装依存で、同じ入力でも一致する保証がない |

ハッシュは FNV-1a を 2 レーン回して MurmurHash3 の finalizer で撹拌した 40bit。
暗号ハッシュ (`crypto.subtle`) を使わないのは、http や古い環境で使えず**そのために版が
出ないほうが困る**ため。用途は改竄検知ではなく突き合わせなので強度は要らない
(20万通りの生成で衝突 0 を確認)。表記は紛らわしい文字 (I/L/O/U) を除いた
Crockford base32 8 文字で、目視・読み上げしやすくしてある。

プレビューページでフェーズ構成を編集すると版も変わる (= 別のデータになった)。
その場合は「（このページでフェーズ構成を変更済み）」と併記して、共有元と違う理由が
分かるようにしている。

回帰テスト: `seed_share.test.cjs` (何で変わる/変わらないか)、`bracket_dom.test.cjs`
(表示・プール/フェーズ切替で不変・編集で変化)、`bracket_page.test.cjs` (配線)。

## 3. ブラケットの組み方

- フェーズ f の参加者: f=0 は全員。f≥1 は **前フェーズまでの予測進出者 = グローバル
  シード上位 Σ(adv×pools)**。進出者を**全体シード順で並べ直して次フェーズを再スネーク**する。

### 進出人数による打ち切り (2026-08-13 実データ検証済み)

予選プールは優勝者を決めないので、**通過者が決まったところでラウンドが終わる**
(2人抜けのプールにグランドファイナルは無い)。`poolDoubleElim(M, adv)` が構造から算出する:

1. 脱落は**敗者側 (と GF) の試合でしか起きない** (bye の試合は誰も落とさない)。
   実施順 `playOrder()` = W1 → L1 → W2 → major → minor → W3 → … → GF に沿って
   脱落数を積み、**残り人数が adv 以下**になったラウンドで打ち切る。
2. その後、**次に脱落者が出るまでの勝者側ラウンドは実施する**。誰も落とさないが
   start.gg は順位決定のために実際に行っている。

実ブラケットとの突き合わせ (`tests/seeding/bracket_core.test.cjs` に固定):

| 実プール | 人数 | 通過 | 勝者側 | 敗者側 | GF |
|---|---:|---:|---|---|---|
| りぷぶらSP15 予選 (phase 2341773) | 11 | 6 | 3,4,2 試合 | 3,2 試合 | なし |
| 篝火15 Phase1 A100 (phase 2132353) | 21 | 12 | 5,8,4 試合 | 5,4 試合 | なし |

いずれも試合数までラウンド単位で一致する (全 bye のラウンドは start.gg 側に作られないので
比較から除く)。最終フェーズ (`adv` 0) は打ち切らず GF まで出す。
ラウンド表示名 (「決勝」「敗者側決勝」) は**打ち切り前のラウンド総数** (`wTotal`/`lTotal`)
基準で付ける。

2 の「勝者側を1ラウンド先まで進める」は **minor (敗者側どうし) で打ち切ったときだけ**。
major (勝者側から敗者が落ちてくるラウンド) で打ち切ったときは、次のドロップを供給する
勝者側ラウンドがまだ走っていないので止まる。実ブラケット4件がこの区別で説明できる:

| 実プール | 打ち切り位置 | 勝者側の続き |
|---|---|---|
| りぷぶらSP15 予選 (11人6抜け) | minor | あり (勝者側準決勝まで) |
| 篝火15 Phase1 A100 (21人12抜け) | minor | あり (勝者側QFまで) |
| りぷぶらSP15 Aクラス (48人8抜け) | major | なし |
| 篝火15 Phase2 D100 (24人3抜け) | major | なし |

### 敗者側スタート (トップカット。2026-08-13 実データ検証済み)

「予選1位は勝者側、2位以下は敗者側から」のような構成は `phases[].lb`
(= 1プールあたり敗者側スタートの人数) で表す。`poolDoubleElim(M, adv, lbStart)`:

- 上位 `w = M - lb` 人が勝者側ブラケット (通常のシード配置)、下位 `lb` 人が敗者側直入り。
- 直入り勢だけで `w` 側の WR1 敗者数 (= Bw/2) まで減らしてから、標準の major/minor 交互に合流。
- 直入り勢の初戦は、上位半分 A と下位半分 B に割り **A[i] の相手が B[i^2] (i<8) / B[i^1] (i>=8)**。
- 敗者側スタート勢は 1 敗で終わるので、総試合数は `M + w - 2` (完全 DE の `2M-2` ではない)。

| 実ブラケット | 構成 | 勝者側 | 敗者側 | 敗者側初戦の組 |
|---|---|---|---|---|
| 篝火15 Phase2 D100 | 24人 = 勝8 + 敗16 (3抜け) | 4,2,1 試合 | 8,4,4,2,2,1 試合 | 一致 |
| りぷぶらSP15 Aクラス | 48人 = 勝16 + 敗32 (8抜け) | 8,4 試合 | 16,8,8,4,4 試合 | 一致 |

  表に無い形のフォールバックも旧来の場当たり式 (i^2/i^1) から XOR 系列に置き換えた。
  修正前は 192人本戦の敗者側直入りペアが実ブラケットと大きく食い違っていた
  (= 「敗者側で予選通過した人の進出先がおかしい」の原因)。

- **勝者側1回戦の例外6件**: M=12 の2件 (同じ M=12 の他3件とは一致)、

  (2019年の並びは現行と違う)。TO の手動シード変更や年代による生成規則の差と考えられる。

**未検証の仮定**: 合流後 (major/minor) のドロップ並び替え規則は標準構成のものを流用している。

### bye の非表示

片方が空きの試合 (bye) と両方空きの試合は描画しない。接続線も、消えた側からは引かない
(両方消えていればその接続線ごと省く)。start.gg も bye の set を作らないので、
実ブラケットとの比較もこの状態で行う。

### start.gg 自動進出との等価性 (2026-08-13 実データ検証済み)

篝火15 の実 API データ (Phase 2 = 64プール1536人 / Phase 3 = TOP192) で
`Seed.progressionSource` を全件突き合わせた結果:

- **Phase 3 の全192席が「シード通りに勝ち上がった場合の保持者の Phase 2 シード番号」と
  席番号まで完全一致 (192/192)**。つまり start.gg の自動進出は、次フェーズの席を
  「期待強度順 (= 元シード順)」に並べる。
- **Phase 2 の席→プール割当は正確なスネーク (1536/1536)**。ただしプールの表示名
  (D100, D200, …) はスネークの列順とは無関係 (ラベルは会場配置等の都合。マッチアップには
  一切影響しない)。

したがって **「進出者を全体シード順で再スネーク」= start.gg 自動進出のデフォルトの
シード通り射影と完全に同じマッチアップ**になる。模倣のための特別なパターン実装は不要。
検証スクリプトの手法: phase の `seeds { seedNum progressionSource { originPlacement
originPhaseGroup { displayIdentifier } } }` を全ページ取得し、帯 (originPlacement) 内の
席順と各プールの期待 n 番手のシード番号を照合。

将来、手動で placeholder を並べ替えた大会や非標準テンプレートに出会った場合に備え、
ペイロードの各フェーズに `prog` フィールド (省略時 = 上記デフォルト) を予約しておく。
カスタムパターンの指定 UI は実例が出てから実装する。

### 敗者側ドロップ規則 (2026-08-13 実データ検証済み)

start.gg の実ブラケット構造は `phaseGroup.sets(filters:{showByes:true})` の
`slots { prereqType prereqId prereqPlacement }` (prereqPlacement 1=勝者/2=敗者) で
グラフとして取れる。これを「シード通り」で伝播させ、`poolDoubleElim` の予測
マッチアップと全ラウンド突き合わせた。

判明した規則: **WRj 敗者の並び替えは「落ちる先の敗者側ラウンド番号 L(2j)」で決まる**
- L4 = 全反転 / L6 = 半分ごとに反転 / L8 = 半分入替 / L10 以降 = そのまま
- start.gg は敗者側の先頭に L1 (bye 詰め) / L2 (WR1 敗者 vs bye) の 2 ラウンドを
  構造として持つ (こちらのモデルの L1 = 先方の L3)。
- 序数ではなくラウンド番号基準である証拠: 敗者側に直接プレイヤーが入るカスタム構成
  (スマバト TOP96 = 32勝者+64敗者スタート、篝火 Phase3 = 64+128) では最初のドロップが
  L6/L8 になり、そこでも L6=半分内反転・L8=半分入替 だった。

検証結果 (シード通り伝播の全ラウンド一致):
- スマパ#241 (64人フルDE・bye無し): 勝者側7 + 敗者側12 ラウンド ✅
- 新京都DSW#64 (28人/B=32)・渋谷達#136 (24人)・シカブラ#104 (24人)・
  上野スマコミ#519 (27人): 各 勝者側6 + 敗者側10 ラウンド ✅ (bye・GF/リセット込み)

残る仮定: L10 以降のドロップが大人数になる B=256 級の深部 (n≥8) は実例が見つからず
「そのまま」と仮定 (篝火 Phase3 は TOP24 打ち切りで L9 まで。観測済みの L10 は n≤4)。
検証ハーネスは scratchpad の gg_lb_verify.js / gg_lb_decode.js 方式 (使い捨て)。
- プール内: 所属メンバーをグローバル順 → ローカルシード 1..M。B = nextPow2(M)、
  `seedSlotOrder(B)` でスロット配置、M < B は bye。
- 勝ち上がり予測: 各ノードで小さいシードが勝つ (`projectedMatches` と同一規則)。
- 敗者側 (v2): 教科書的ダブルイリミネーションのドロップ配置。start.gg の rotation は模倣しない。

### 次フェーズのどこから始まるか (2026-08-13 修正)

前フェーズを**無敗のまま**通過した人だけが次フェーズの勝者側から始まる。
1敗して (= 敗者側を勝ち上がって) 通過した人を勝者側に置くと「敗者側から勝者側に上がる」
ことになってしまうため、`phases[].lb` を明示していないフェーズは

    1プールあたりの敗者側スタート = プール人数 − ceil(前フェーズの無敗通過者数 / このフェーズのプール数)

を既定値にする (`lbOfPhase`)。`poolDoubleElim` が返す `undefeated` (通過者のうち
一度も敗者になっていないローカルシード) から算出する。敗者側スタート勢は最初から1敗扱いなので
勝ち上がっても `undefeated` には入らない。

例: 24人 = 勝者側8 + 敗者側16 の6抜けでは、通過6人のうち無敗は2人だけなので、
次フェーズは 2人が勝者側・4人が敗者側スタートになる。

**ズレを作らないための扱い** (2026-08-13):
- フェーズ構成エディタには既定値がプリフィルされ、**触らなければ `lb` を保存しない**。
  前フェーズの進出人数などを変えると自動で追い直す (適用時に「入力値 == 既定値」なら省く)。
- 明示的に別の数を入れたときだけ固定値として保存する。実構成がそうなっている大会もあるため
  禁止はしないが、**食い違っていればステータス行で警告する**:
  「⚠ 前フェーズを無敗で通過したのは4人ですが、勝者側スタートは8人の設定です —
  1敗で通過した人が勝者側から始まります」。
- プール情報にも「勝者側スタート◯人・敗者側スタート◯人 / 前フェーズの無敗通過◯人」を出す。

### 次フェーズの入り口表示 / 前フェーズの出どころ

各選手が最後に出る試合の枠に「→ P1 #7 敗者側」のようなチップを出す。
中身は次フェーズでの プール / そのプール内のシード番号 / 勝者側・敗者側スタートの別で、
クリックするとそのフェーズ・プールを開いて本人をハイライトする (`hi=<index>` を
フラグメントに入れるので、その状態のまま共有できる)。通過しない選手・最終フェーズでは出ない。

逆向きに、フェーズ1以降では**各選手が最初に出る枠に「← A1 #2」**(前フェーズのプールと
そこでのシード番号) を出す。クリックすると前フェーズのそのプールへ戻り、本人をハイライトする。

### プール内の行き来 (2026-08-13)

- **勝者側の負ける側の枠に「↓ 敗者側○回戦」**を出す。クリックでその試合へスクロールし、
  本人をハイライト + 一瞬光らせる (敗者側が非表示なら表示に切り替えてから飛ぶ)。
  落ちる先は「その選手が敗者側で最初に現れる試合」で引く (打ち切りで組まれていなければ出さない)。
- 敗者側の枠には**「↓勝者側○回戦」= どこから落ちてきたか**を出す。その選手が敗者側で
  初めて出る枠にだけ付けるので、ドロップ戦 (major) だけでなく敗者側1回戦のような
  ペアリング戦にも出る。クリックで元の試合へ戻れる。敗者側スタート勢は勝者側に出ていないので出さない。
- 敗者側は勝ち上がりの色を橙系にして勝者側 (青) と区別する。
- **接続線はスロット単位**で結ぶ (前の列のその選手の枠 → この列で入る枠)。誰が次のどこへ
  行くかを線で追えるようにするため。形は水平→垂直→水平の折れ線で、曲線は使わない。
  **左に対応する枠が無い側には線を引かない** (勝者側から敗者側へのドロップ、GF の敗者側優勝)。
  どこから来たかは枠内の「↓勝者側○回戦」バッジで示す。
- **勝ち上がる側を上のスロットに描く**。敗者側の構造は a=生き残り / b=ドロップ の並びなので、
  そのままだと勝つ側が下に来る。表示順だけ入れ替える (a/b の役割は変えないので、
  ドロップ判定や初登場判定はそのまま)。
- **名前クリックでその選手をハイライト** (もう一度で解除)。通過しない選手も対象なので、
  「この人はどこで負けてどこに落ちるか」を追える。ハイライトは同じプール内の全出現枠に付く。
- **枠 (試合カード) の中と外の切り分け** (2026-08-13):
  - フェーズをまたぐ導線は**枠の外**。進出先「→ P1 #2」は右外、出どころ「← A1 #2」は左外に
    絶対配置する (`.bp-slot` を基準に `left:100%` / `right:100%`)。はみ出しぶんは
    `.bp-bracket` の左右パディングで確保する (左はフェーズ1以降のみ = `has-prev`)。
  - それ以外のタグ (居住地・落ちる先・落ちてきた元) は**名前の下・同じ枠の中**
    (`.bp-line` = シード/キャラ/名前、その下に `.bp-tags`)。タグが無ければ行自体を出さない。
- 選手データの**再取得ボタンは取得失敗があるときだけ表示**する
  (失敗は次の描画で自動リトライされるので、普段は出す意味がない)。

## 4. プレビューページ UI

- **フェーズタブ → プール選択** (ウェーブごとにグルーピング表示) → 右に進む標準ブラケット。
- スロット表示: シード番号 / 名前 / 居住地 (都道府県 or 国名。地域グループはバッジ色で表現、
  bye はグレー)。SPSP 未登録者は名前のみ + 「未登録」表記。
- 勝者ラインを強調し、次ラウンドへ予測勝者を自動表示。
- **マッチアップ注記** (予測対戦カードすべて、後ラウンド含む):
  - 同居住地 (同一都道府県/地域グループ/同一国) → 色バッジ。
  - 直近対戦あり → 「3週間前」等の相対表示。クリックで `recentMeta.matches`
    (日付・大会名・規模) の一覧ポップアップ。
  - `wd` トグル (平日大会を含む/除く) = `buildSeedData` の `excludeWeekday` に直結。
    切替時は集計だけ再実行 (取得済み JSON はキャッシュ)。
- **名前クリック → 概要ポップアップ**: SPSP 表示名・順位/スコア (`ranks`/`scores`)・
  居住地・直近の大会成績 (`tournaments` 先頭数件)・「プレイヤーページへ」リンク (`/p/?uid=`)。
- **フェーズ構成エディタ**: フェーズの追加/削除、プール数・進出人数の変更。変更で blob を
  再エンコードし URL 更新。妥当性チェック (進出合計 ≤ 前フェーズ人数、pools ≥ 1 等) は fail-loud。
- **CSV import**: 作業状況CSV (`seed,name,discriminator,uid,lock,pool,pools,waves`) を
  ドロップ/選択で読み込み、ペイロードを構築して表示 + URL 更新。Discord 等には
  このファイルを渡してもらう運用。
- デコード失敗・データ欠損は黙って劣化させず明示 (seed_data の fail-loud 方針を踏襲)。

### データ読み込み戦略

1. blob 復号 → フェーズ/プール構造を構築 (通信なし)。
2. `player_prefectures.json` + `overseas.json` を一括読み (居住地の即時表示用)。
3. プール表示時にそのメンバーの `players/<uid>.json` を遅延取得 (並列 8、キャッシュ)。
   **表示名 (`display`)**・海外勢の国名 (`country_ja`)・直近対戦集計はここから。
   `buildSeedData` を「プールメンバーのみの ranking」で呼ぶ (ペア集計はプール内だけで十分)。
   取得完了までスロットは `#シード番号` のプレースホルダ表示。

## 5. 発行側 (seed_app.js)

- 手動調整バー付近に「トーナメントプレビュー」ボタン。
- 押すと小ダイアログ: イベント名 (自動入力) + フェーズ構成の初期値
  (既定 = 現在のプール数で 1 フェーズのみ。Top カットを任意で追加) → 「リンクを発行」。
- 並びは `orderedRecs()` (被り回避/手動/CSV/固定 適用後の最終表示順) をそのまま使う。
  プール数 = `so-pools`、ウェーブ = `currentWaveMap(P)` から `wv` を構築。
- 別タブで開く + クリップボードへ URL コピー。URL 長が閾値 (~8万字) を超える場合は
  警告して CSV 運用を案内。
