# シード生成：直近再対戦回避 & 地域被り回避 — 設計＆実装ドキュメント

> ステータス: **実装完了**（`site/seeding/` モジュール + `site/seed/` 統合 + `tests/seeding/` 71件）。
> 本ドキュメントは確定仕様。実大会(スマバト#67/池スマ#4)でチューニング・検証済み。
> 対象ページ: `site/seed/`（シード生成）。将来: CSV アップロード型の被り回避ページでも再利用予定。

---

## 1. 目的とスコープ

スマブラSP大会のシードを、SPSP ランキング順を尊重しつつ

- **地域被り回避**（同じ都道府県の選手が早期に当たるのを避ける。**最優先**）
- **直近再対戦回避**（最近対戦したばかりの相手と早期に当たるのを避ける）

の2目的で最適化する。計算は**全てユーザーのブラウザ（フロントエンド）**で行う。

入力は「**プール数**」と「**ランキング（シード順）**」、出力は「**最適化済みシード順**」。
ランキングを受け取りシード順を返す純粋関数として実装し、専用 JS モジュールに閉じる。
シード生成ページはモジュールを呼んで結果を表示するだけにする。

## 2. 全体アーキテクチャ

### 2.1 モジュール構成（3層、相互独立）

```
┌─────────────────────────────────────────────────────────────┐
│ ページ (site/seed/index.html, 将来: CSV被り回避ページ)        │
│   - ランキング/プール数/形式の入力UI                          │
│   - 進捗・途中経過・中断ボタン・上級者パラメータ・レポート表示  │
│   - 取得モジュール → 計算モジュール(Worker) を呼ぶだけ        │
└───────────────┬───────────────────────────┬─────────────────┘
                │                           │
   ┌────────────▼────────────┐   ┌──────────▼──────────────────┐
   │ seed_data.js            │   │ seed_optimizer.js           │
   │ （データ取得・集計層）   │   │ （純粋計算層 / Worker内実行） │
   │ - players/<uid>.json取得 │   │ - 取得/DOM/通信に一切依存しない │
   │ - 都道府県map            │   │ - 入力: ランキング+構築済データ │
   │ - 都道府県別出場人数      │   │ - 出力: シード順+プール+レポート │
   │ - ペア直近対戦罰則(疎)    │   │ - 山登り/SA/多点 をここに実装  │
   └─────────────────────────┘   └─────────────────────────────┘
```

- **`seed_data.js`**: 取得・集計のみ。fetch を行うが DOM には触れない。出力は「計算層が消費できるデータバンドル」。
- **`seed_optimizer.js`**: **純粋**。fetch も DOM も使わない。入力は `ranking` と「事前構築済みデータ（都道府県・ペア罰則など）」のみ。Web Worker 内で実行する前提で、`postMessage` 可能なプレーンデータだけを受け渡す。
- ページは両者を繋ぐだけ。将来の CSV ページも同じ2モジュールを使い、入口（ランキングの作り方）だけ差し替える。

### 2.2 非ブロッキング実行（Web Worker）

計算は重くてよいが UI を止めない。**`seed_optimizer.js` は Web Worker で実行**する。

- メイン→Worker: `{type:'start', input}` / `{type:'stop'}`
- Worker→メイン:
  - `{type:'progress', phase, iter, bestScore, ...}`（頻繁・軽量）
  - `{type:'checkpoint', snapshot}`（区切りごと。途中経過の seed 順と暫定スコアを含む）
  - `{type:'done', result}` / `{type:'error', message}`
- **中断**: メインが `stop` を送ると、Worker は「現時点の best」を `done` で返す（途中で止めて最後の結果を反映できる）。
- 取得層（`seed_data.js`）はネットワーク I/O 主体なのでメインスレッド（または別途取得用 Worker）で実行し、進捗をUIに流す。計算 Worker とは分ける。

## 3. データモデル

### 3.1 取得元（全てフロントで取得可能・確認済み）

| データ | 取得元 | 備考 |
|---|---|---|
| 居住地（都道府県） | `data/player_prefectures.json`（`{uid: 都道府県漢字}`）＋必要なら各 `players/<uid>.json` | 未登録 uid は **null（罰則なし）** |
| 過去対戦履歴 | `players/<uid>.json` の `recent_matches[]` | 各要素に `opp_uid` / `date` / `event_id` / `round` あり。実質**全履歴**（例: 1選手で ~4.5年・2300件） |
| 大会規模（参加人数 nent） | 同 JSON の `tournaments[]`（`event_id → nent`） | マッチの `event_id` から結合可能 |
| プール予選形式 | start.gg API `phase.bracketType`（保存データは `bracket_type`） | `DOUBLE_ELIMINATION` / `SINGLE_ELIMINATION` / `ROUND_ROBIN` 等。**取得できなければ DE 想定**（§5） |
| アカウント統合表 | `data/user_merges.json`（`{old_uid: 正規uid}`、`build/user_merges.py` から生成） | seed ページが entrant の `user.id` を `canonicalUserId()` で正規化してから全処理に流す。旧アカウントでエントリーされてもランキング・対戦履歴が正規 uid で引ける |

### 3.2 ペア直近対戦罰則の構築（疎行列）

全ペア O(N²) を総当たりせず、**実際に対戦したペアだけ**を疎に持つ:

```
for 各出場者 a:
  a.recent_matches を走査
  for 各マッチ m (opp_uid = b):
    if b も出場者:
      key = ordered(a,b)         // 小さいuid:大きいuid
      val = dateDecay(m.date) * sizeWeight(nent(m.event_id))
      recentPair[key] = (recentAgg=='max') ? max(recentPair[key], val) : recentPair[key] + val
```

- 両者の JSON に同じマッチが入るため、**両方向を走査しつつ試合キー**
  `(pair, event_id, phase_name, round, round_text, date)` **でデデュープ**して二重計上を防ぐ。
  （旧仕様の「`a<b` の片側のみ集計」は、低 uid 側が DB 未登録(404)のとき高 uid 側に記録が
  あっても罰則が消える＝どちらが消えるかが uid の偶然で決まるため廃止。）
- **ペア内集計 `recentAgg`（既定 `max`）**: 同じ2人が複数回対戦した分の罰則のまとめ方。
  `max` はそのペアの最も重い1試合だけを採用し、対戦回数に依らず横並びにする（実大会 TO WIN#10
  で sum より早期被りが微減・常連カードの分離も同等以上）。`sum` は全対戦を合算し、頻度の高い
  常連カードほど重く＝強く分離する旧挙動。上級者モードで切替可。
- 計算量は Σ(各出場者の対戦数) に比例＝現実的。
- **`recentMeta[key].matches`**: ペアごとの個別対戦履歴 `[{date, tournament, nent}]`（新しい順）。
  decay>0 の期間内・dedup 後・excludeWeekday 適用後の試合のみ。レポートの直近対戦ペアを
  タップすると展開される履歴リストのデータ源（optimizer はレポート item の `matches` に素通しする。
  matches の無い旧形式 recentMeta では `null`）。
- **平日大会の除外 `excludeWeekday`（既定 `false`）**: `true` なら平日扱いの大会
  （`is_weekend=false` ＝ 平日開催・実質平日シリーズ・プレ大会）での対戦を集計から除外する。
  休日/平日の判定表は**出場者全員の `tournaments[]`** から `event_id → is_weekend` を先に構築
  （片側の JSON にしか大会情報が無くても対称に判定）。表に無い大会（`is_weekend` 不明）は
  **除外しない**（保守的に再対戦回避の対象へ残す）。除外したユニーク試合数は
  `meta.weekdayExcludedMatches` で返し UI に明示する。UI は「平日大会の対戦を除く」チェックボックス。

### 3.3 都道府県別出場人数

出場者の `prefByUid` を集計し `prefCounts[pref] = 人数`。地域被り罰則の重みに使う（§6.1）。

## 4. プール / ブラケット形状

### 4.1 プール割当（snake / serpentine）【実データで確定】

全 N 人をシード 1..N（1 が最上位）に並べ、P プールへ蛇行配置する（start.gg 標準 serpentine）。
**確定式**（`s = seed_num − 1`, 0始まり）:

```
row  = ⌊ s / P ⌋                       // 行 = プール内順位（0始まり）
col  = s mod P
pool = (row が偶数) ? col : (P − 1 − col)   // 0始まりプール番号。奇数行は左右反転
```

```
行(=プール内順位) 1: seed 1 → P1, seed 2 → P2, …, seed P  → PP      (左→右)
行            2: seed P+1 → PP, …,            seed 2P → P1      (右→左)
行            3: seed 2P+1 → P1, …                              (左→右)
…
```

- **プール内順位** = その選手がいる行番号（1始まり、小さいほど上位）。
- **検証**: 実大会「みどブラSP#3 TOP160」(4プール DE, 155 seeds) を `matches.json`(phase_group_id) × `seeds.json` で突合し一致を確認:
  - P1=`{1,8,9,16,17,24,25,…}` / P2=`{2,7,10,15,18,…}` / P3=`{3,6,11,14,…}` / P4=`{4,5,12,13,…}`。
- **端数行（N が P で割り切れない）**【#3 確定】: 最終行はその行の蛇行方向に**先頭プールから順に**埋まり、**末尾側プールが1人少ない**。プールサイズ差は最大1。
  - 例: 155÷4 → 1〜38行が満杯(152人)、39行目(seed 153,154,155)は左→右で P1,P2,P3 に入り、**P4 のみ 38 人**（実データと一致）。
  - 「プール内順位が等しい2人」の交換は、満杯行同士・部分行同士でのみ可（行サイズが揃う範囲）。

### 4.1.1 bye 配置【標準】

- ブラケットサイズ `B = 2^⌈log2 M⌉`。`B − M` 個の bye は**上位シードに付与**（seed1 から順に1回戦 bye）。start.gg 標準。
- 上記検証大会でも seed1 等の上位は1回戦 bye（`matches.json` に1回戦の対戦が無い）で整合。

### 4.2 プール内ブラケット（勝者側のみ）

- プール内トーナメントは**勝者側のみ**を考える（DE でも敗者側は無視）。
- プールサイズ M に対しブラケットサイズ `B = 2^⌈log2 M⌉`。不足分は **bye**（標準では上位シードに付与）。
- ブラケット内のスロット割当は **start.gg 標準シード**（seed1 と seed2 が決勝でのみ当たる蛇行配置）。

### 4.3 「当たりうるペア」と最早対戦回戦

スロット 0..B-1（0始まり）に標準シードで配置したとき、2 スロット `p,q` の**最早対戦回戦**は

```
earliestMeetRound(p,q) = min{ t : ⌊p / 2^t⌋ == ⌊q / 2^t⌋ }      (t = 1,2,…,k)
```

（サイズ 2^t のグループに初めて同居する回戦 t で当たりうる。t=1 が1回戦）。
単一ブラケットでは**任意のペアがいつかは当たりうる**ので、プール内最適化では全ペアを対象に、この回戦に応じた重み（§6.3）を掛ける。

## 5. 最適化フローの分岐（確定）

| | プール予選 = DE | プール予選 ≠ DE |
|---|---|---|
| **2プール以上** | プール間最適化 → プール内最適化 | プール間最適化のみ |
| **1プール** | プール内最適化のみ | **非対応**（「このプール形式は被り回避非対応」と表示し計算しない） |

- プール内最適化は **DE プールのときだけ**実行する。
- `1プール × 非DE` は計算せず、非対応メッセージを出す。
- **形式の取得**: start.gg API の `phase.bracketType` を読む。指定が取得できない（phase 未作成等）場合は **DE 想定**で進める。

### 5.1 勝者側ブラケットスコープ（`bracketScope: 'winners'`）

プール最適化に**追加**する勝者側フェーズ。P>=2 では通常どおり inter → intra を
実行した後、グローバルシード列全体を 1 つの勝者側 DE ブラケットとみなした
追加フェーズ (タイ帯内 swap) を重ねる。追加フェーズの delta にはプール成分
(inter ペア罰則 + intra 回戦重み) も含まれるので、プール分離を壊す移動は
損として評価される (= 合成目的関数の純追加)。P==1 は勝者側フェーズのみ
(「当たりうる」ベースの intra は使わない)。このスコープでは **全フェーズで
DE 想定順位 (タイ帯) 不変** がハード制約になる (keepDePlace 強制)。
レポートの評価値には `winners` 成分が加算され、レポート自体は実 P の
プール視点 (①〜④) + 予選抜け後 (⑤)。

- **目的関数は「シード通り勝ち上がったときに実際に発生する試合」のみ**
  (`projectedMatches`: 各ブラケットノードで左右サブツリーの最小シード同士が当たる、
  bye 除き N−1 試合)。「当たりうる」全ペアは考慮しない — 例えば seed1×seed5 は
  R2 で当たり得るが、シード通りなら 4 が 5 を倒すので対戦せず、罰則にも入らない。
  試合は位置ペアで固定なので swap の delta は O(log B)（各位置の対戦相手数）。

- **ハード制約は「DE 想定順位（タイ帯）不変」のみ**。タイ帯は 1,2,3,4 が単独帯
  （= トップ4は不動）、以降 {5,6},{7,8},{9..12},{13..16},{17..24},… と広がる。
  帯内の入替は全員の想定順位を変えないので、swap 近傍を帯内に限定するだけで
  制約が恒等的に満たされる（`keepDePlace` と同じ origRank 基準の判定）。
- **可動制約（kInter/kIntra/enableIntra）は適用しない**。プール内順位の固定や
  ±幅の制限なしに帯内で自由に動ける。移動の抑制は W_order（シードズレ罰則、
  `|Δseed|^orderPow`）の正則化で連続的に制御する。`maxSeedShift` だけは
  指定時に有効（帯より狭くしたいとき用）。
- **回戦重みの既定は winners 専用生成 `winnersRoundWeights(rounds)`**:
  R1=1, R2=0.5, R3 以降は 0.2 から毎回戦 ×0.9 の緩やかな単調減少をブラケット
  全深さぶん生成。R1,R2 の早期被りを強く避けつつ、後段も「当たりを遅らせる」
  こと自体に僅かな価値がある（決勝まで勾配あり、R8 でも ~0.12 で無視されない）。
  プール用既定 `[1,.6,.4,.06,.02]` は R5+ が 0.02 とほぼ無視になるため使わない。
  `roundWeights` 明示時はそれが優先。
- **DE 専用**（非 DE は unsupported）。プール数はレポート・最適化に関与せず、
  出力 `pools` の serpentine 導出（適用時の割当表示）にのみ使う。
- レポートは P=1 視点（= 勝者側ブラケットの早期回戦被り報告。改善率は
  intra 成分基準 = P==1 と同じ扱い）。
- UI トグル: 「勝者側ブラケットで最適化」（既定 OFF）。
- オプション `winnersPoolRankLimit`（UI「└ プール内順位の制約」・既定 OFF）:
  タイ帯不変に加えて、従来 kIntra と同じ規則をプール内順位 (snake 行番号) に適用する。
- 進捗: `optimize()` は `searchStats`（phase 別 iters/maxIters）を返し、worker の
  checkpoint は `roundStats` と `intermediate`（ベスト解の完全な結果）を載せる。
  UI は各ラウンドのステップ数% と、ラウンド終了ごとの中間レポートを表示する。
- レポート追加セクション `residualConcerns.postPool`（両スコープ共通）:
  全体を 1 つの勝者側ブラケットとみなし、シード通り勝ち進んだ場合に
  earlyRound (既定3) より後の回戦で当たる 直近対戦/同一地域 ペア =
  「予選抜け後 (本戦想定) の再対戦・地域被り」。プール構造とは独立の見積もり。

## 6. 評価関数

各マッチ（＝当たりうる1ペア）の罰則:

```
pairPenalty(a, b) = W_region · regionPenalty(a, b) + W_recent · recentPenalty(a, b)
（W_region と W_recent の大小は自由。既定は地域優先の 1.0 / 0.3。2026-07 に大小強制を撤廃）
```

**オンオフトグル**（UI／`params`）: 各罰則・プール内変動は個別に無効化できる。
- `avoidRegion`（既定 ON）: false で地域成分を完全に 0（`W_region` 比較・レポート地域スコアも無効）。
- `avoidRecent`（既定 ON）: false で直近成分を完全に 0。
- `enableIntra`（既定 ON, **P≥2 のみ有効**）: false でプール内変動（intra 最適化）を行わない。
  1プール×DE では intra が唯一の被り回避なので、このトグルは無視され常に実行する。

最適化対象の総スコア（**小さいほど良い**）:

- **プール間**: 各プール内の**全ペア**に `pairPenalty` を適用し総和。
  ```
  F_inter = Σ_{pool} Σ_{a<b ∈ pool} pairPenalty(a, b)
  ```
- **プール内**（プールごと、勝者側で当たりうる全ペア）: 最早対戦回戦の重みを掛けて総和。
  ```
  F_intra(pool) = Σ_{a<b ∈ pool} roundWeight(earliestMeetRound(a,b)) · pairPenalty(a, b)
  ```

### 6.1 地域被り罰則 regionPenalty（提案デフォルト）

```
regionPenalty(a,b) = (pref 既知 かつ pref(a)==pref(b)) ? prefWeight(pref(a)) : 0
prefWeight(p)      = 1 / sqrt(prefCounts[p])     // 人数が少ない県ほど大きい（連続重み）
```

- **設計思想**: 県ごとの連続重み（既定 `1/√人数`）のみ。少数派を特別にハード罰則しない＝
  **重みに応じてどの県もいい感じに分散**する。人数が多い県（例: 関西大会の大阪）は鳩の巣で
  被り不可避なので相対的に軽く、人数が少ない県は重く扱われ優先的に散る。
- 例: 2人なら 1/√2≈0.71、9人なら 1/3。
- 都道府県不明の選手は罰則 0。
- **地域グルーピング**: 被り回避では近隣県を同一地域として扱う。`seed_data.buildRegionGroups({…})`
  でトグル指定し `regionGroups` に渡す。定義は `REGION_GROUP_DEFS`:
  - `minamiKanto`（既定 **ON**）: 南関東＝埼玉・千葉・神奈川・東京。
  - `keihanshin`（既定 **OFF**）: 京阪神＝兵庫・大阪・京都。
  統合後は東京×神奈川等も「同一地域の被り」として扱い、人数も合算（=大都市圏は
  大グループ＝鳩の巣で不可避＝相対的に軽い）。表示用の都道府県には影響しない。
- **ハイパラ**: `prefWeight`（`inv_sqrt`/`inv`/`inv_log`/`const`）、`regionGroups`。

### 6.2 直近対戦罰則 recentPenalty（提案デフォルト）

```
recentPenalty(a,b) = Σ_{過去のa,b戦 m} dateDecay(Δdays) · sizeWeight(nent(m.event))

dateDecay = 制御点 [[日,重み],…] の線形補間（最後の点より後は0）
  既定: 0:1 / 30(1ヶ月):1.0(フル) / 91(3ヶ月):0.5 / 182.5(半年):0.25 / 365(1年):0（直後の再戦を徹底回避）
sizeWeight(nent) = log2(nent)                        // 参加人数が多いほど大きい
```

- 制御点間を線形補間。1ヶ月/3ヶ月/半年に差をつけ、半年以降は急減（点を詰める）。
  最後の点(1年)より後は罰則 0（疎行列に載らない）。
- §3.2 の疎行列に事前計算済みの値をそのまま使う。
- **ハイパラ**: `recentDecayPoints`（[[日,重み],…] の制御点）/ `sizeWeight`。UIは "日:重み,…" のCSVで編集。

### 6.2.1 同シリーズ再マッチ罰則（既定 OFF・2026-08）

「今回シードする大会と同じシリーズで既に当たっているペア」を、通常の再戦より重く罰する。
「また篝火で同じカードになる」のを避けたいとき用。UI は「同シリーズの再戦を強めに避ける」
チェックボックス（既定 OFF）＋ 対象シリーズの選択欄。

```
seriesPenalty(a,b) = 同シリーズの対戦だけを recentPenalty と同じ規則
                     (dateDecay × sizeWeight, max/sum 集計) で集計したもの

倍率 (既定):  pp = W_region·region + W_recent·recent · (同シリーズ対戦あり ? seriesMult : 1)
加算:         pp = W_region·region + W_recent·recent + W_series·seriesPenalty
```

**対象シリーズの判定**（`seed_data.js`）: シリーズ名は大会名から番号・サブタイトルを剥がして
作られる（サーバ側 `spsp/meta.py: tournament_series`）。その規則をブラウザで再実装すると
二重管理で必ずズレるのでやらない。代わりに `site/data/tournaments.json` の
`event_id → series` を正解表として使う:

1. 取り込み済みの大会は `event_id` で正確に引く
2. 未取り込み（＝これから開催する大会）は「大会名に含まれる最長の既知シリーズ名」で推定
   — 既存 5,399 大会での照合で **93.3% 一致**

推定は外れうるので、判定結果は必ず UI に出し、`<select>` で選び直せるようにしてある
（黙って別シリーズの罰則を掛けない）。ON なのに未選択のまま実行しようとしたら止める。
`tournaments.json` は約 3MB あるので、**チェックを ON にしたときだけ**取りに行く。

#### 倍率 vs 加算の検証（2026-08）

実データ 9 大会（篝火#15 / グラスラ#19 / 九龍#18 / スマバト#67 / 西武撃 / クロブラ /
池スマ / IMPACT MAJOR / カリスマSP23、各 256 人まで）を「開催日前日時点の対戦履歴」に
巻き戻して再シードし、乱数 3 種の平均を取った（`keepDePlace: true`, restarts=6）。

| 方式 | 同シリーズ再戦:同プール | 早期回戦 | 通常再戦:同プール | 地域:分離可 |
|---|---|---|---|---|
| OFF | 25.3 | 6.0 | 294.3 | 11.0 |
| 加算 W=0.3 | 17.3 | 4.3 | 297.7 | 11.0 |
| 加算 W=0.6 | 16.0 | 3.7 | 313.3 | 14.0 |
| 加算 W=1.2 | 12.0 | 3.7 | 311.7 | 12.3 |
| 加算 W=2.4 | 9.3 | 1.7 | 313.7 | 14.7 |
| **倍率 ×2** | 13.7 | 2.7 | **302.3** | **10.3** |
| **倍率 ×3** | **11.0** | 1.7 | **302.7** | 11.3 |
| 倍率 ×5 | 8.3 | 1.0 | 323.7 | 12.3 |
| 倍率 ×10 | 8.3 | 1.3 | 316.3 | 11.0 |

**倍率の方が効率が良い**。同シリーズ再戦を同じだけ減らしたとき（12 前後）、加算は通常再戦が
+17.4 増えるのに対し倍率は +8.4 で済む。理由は集計方式にある: `recentPair` は既定で
「そのペアの最重 1 試合」なので、常連ペアの最重試合はたいていそのシリーズの試合。
つまり加算 W=0.3（= `W_recent` と同値）は実質「倍率×2」と同じで、それ以上効かせるには
W を上げるしかなく、同シリーズで軽く 1 回当たっただけのペアまで過剰に罰してしまう。
倍率は「同シリーズで当たったことがあるか」という二値で一律に増幅するので、目的
（そのシリーズでの再戦を避ける）と形が合っている。

→ 既定 `seriesMode: 'mult'` / `seriesMult: 3.0`（同シリーズ再戦 −57%、通常再戦の悪化 +2.9%）。
加算方式も上級者向けパラメータとして残す（`seriesMode: 'add'` / `W_series`）。

**レポート**: プール間・プール内・予選抜け後の各セルに「うち『〈シリーズ名〉』で対戦済 N 組」を
出し、ペア行と対戦履歴の該当試合に ◆ を付ける。罰則 OFF でも件数は出す（気づけるように）。

回帰テスト = `tests/seeding/series_rematch.test.cjs`。


## 7. 探索アルゴリズム

共通: §6 のスコアを**山登り法**で最小化。**多点スタート**・**焼きなまし(SA)**・**その組合せ**を選べる。
**既定モード = 多点スタート焼きなまし**。

### 7.1 1ステップ操作（近傍）

- **プール間**: **プール内順位が等しい2人**（同じ行・別プール）を交換。蛇行構造を保つ。
- **プール内**: 同一プール内の2人の**ブラケット位置（プール内順位）**を交換。

### 7.2 可動制約（**初期順位**基準。前ステップ基準ではない）

各選手は「初期位置からの移動量」に上限を持つ。交換は**両者が各自の窓内に収まる場合のみ**有効。

- **プール間** `k_inter(row)`: プール内順位 row の選手が初期プールから動ける**プール数**。
  - デフォルト: `k_inter(row) = (row≤2)?0:2^(row−3)`（1・2位=固定, 3位=±1, 4位=±2, 5位=±4, 6位=±8, …倍々）。上限はプール数で実質頭打ち。**ハイパラ（配列）**。
- **プール内** `k_intra(rank, M)`: プール内順位 rank（プールサイズ M）の選手が初期位置から動ける**順位数**。
  - デフォルト方針: 「上位1/4=0=固定, 残り=±1」。最大可動1順位。**プール間移動した選手にも同じ窓を適用**（固定しない）。
  - デフォルト式: `rank ≤ M/4 → 0 / それ以外 → 1`。
  - 実大会で R1–R2 はほぼ一掃（例: スマバト#67 で R1:0 R2:0）。**ハイパラ（配列/式）**。
  - 旧実装にあった「プール間移動した選手はプール内固定」の連動制約は**撤廃**（2026-07）。
    実大会5例のベンチで参加者の約8割が固定され早期再対戦回避の主なボトルネックだった。
    撤廃後は早期(R1–R2)再対戦が概ね 1/2〜1/3 に減り、合成変位は加算
    （inter 行内 ≤P−1 + intra ±1行 = 最大 2P−1 シード）に収まる（P=8 実測 dispMax 14-15）。
- **シード変位上限** `maxSeedShift`: 最終シード**番号**が元順位から動ける最大数（inter+intra 合成後）。
  デフォルト `null`（無制限）。k 制約はプール/順位単位のため snake 番号上は最大 2P−1 動き得る。
  番号ベースで直接キャップしたいとき用（0=完全固定）。inter は交換先シード位置、
  intra は交換先のグローバルシード位置を元順位と比較して両者とも窓内の交換のみ許可。
- **DE 想定順位不変** `keepDePlace`（ライブラリ既定 `false`・**UI 既定 ON**）: `true` なら全員の
  DE 想定順位（`dePlaceOfSeed`: 1,2,3,4,5,5,7,7,9×4,13×4,…のタイ帯）が**元シードから不変**の
  交換のみ許可。同タイ帯内の移動（例: シード 13↔15）は自由、タイ帯を跨ぐ移動（例: 8↔9）は禁止。
  maxSeedShift と同じく初期順位基準・inter/intra 合成後のシード番号で判定。
  UI は「DE想定順位を変えない」チェックボックス（既定チェック済み。checked 状態を常に明示送信
  するため、API 既定 false とのズレは実運用に影響しない）。

### 7.2.1 近傍の生成（候補集合方式・2026-08）

7.2 のルールは**すべて判定基準が初期位置**（`origRank` / `initPool` / `initRank`）なので、
「その選手が行き先スロットに座れるか」= `(選手, 行き先)` だけの述語 `posOk` に分解できる:

```
swapAllowed(i, j)  ≡  posOk(order[i], j)  &&  posOk(order[j], i)
```

盤面に依存しないため、各選手の候補スロット集合は**フェーズ開始時に1回作れば以後不変**
（swap ごとの更新も不要。実測では候補集合は常に区間になるが、実装は配列＋Set で持つ）。
近傍生成は「可動スロットを一様に引く → その占有者の候補集合から行き先を引く →
相手側の1チェック」になり、最後に必ず `swapAllowed` を通して再確認する
（候補集合が誤っていても**制約違反の手は出さない**。正しければ常に通過する）。

旧実装は「ランダムにペアを引き、`swapAllowed` を満たすまで最大40回引き直す」方式だった。
`k_intra` の既定（上位1/4固定・残り±1）では有効な行き先が M 個中2個しかないため、
**intra は平均15回超の引き直し・40回失敗が 8〜14%**（`maxSeedShift` 併用時は平均29回・失敗55%）。
失敗は `runSearch` の `if (!nb) break` でリスタートごと打ち切るので、
**intra は反復予算の 0.1% 未満しか消化できていなかった**（実測 240,000 反復中 15〜375）。
候補集合方式では引き直しが intra 2.1回 / inter 1.2回 / winners 1.0回、40回失敗は 0% になり、
`!nb` が「有効手が本当に存在しない」を意味するようになったので `break` も正しくなる。
`maxSeedShift` / `shiftLimitRanks` 併用時に intra が事実上停止していた問題もこれで解消する。

- 引き換えに intra が予算を使い切るようになるため実行時間は約2倍（256人/16プールで
  worker 相当 15 ラウンド 0.95s → 1.86s）。品質は intra 単体で −2〜−31%、total では
  データ次第で ±1% 程度（intra の探索空間は各自 ±1 順位と小さく、200 反復で収束する）。
- 回帰テスト = `tests/seeding/move_candidates.test.cjs`。`params._verifyMoves`（テスト専用）を
  立てると、候補集合から導いた交換可能関係が `swapAllowed` と一致するかを全ペア総当たりで検証する。

### 7.3 山登り / SA / 多点

- **山登り**: 近傍を1つ提案 → Δスコア ≤ 0 なら採用。改善が一定回数出なければ収束とみなす。
- **SA**: Δ>0 でも確率 `exp(−Δ / T)` で採用。`T` を初期値から冷却（幾何冷却 `T ← T·α`）。
- **多点**: 制約内のランダム初期解を K 個生成し各々最適化、**最良を採用**。
- **多点×SA**（既定）: K 個の初期解それぞれに SA。
- **差分評価**: 交換は当該2選手を含むペア項のみ変化 → Δを増分計算（高速化）。

### 7.4 ハイパーパラメータ（探索系）

| パラメータ | デフォルト（案） | 説明 |
|---|---|---|
| `mode` | `multistart-sa` | `hillclimb` / `sa` / `multistart-hillclimb` / `multistart-sa` |
| `restarts` (K) | 15 | 多点スタート数 |
| `iters` | 自動（収束 or 上限） | 1スタートあたり最大反復 |
| `T0` / `cooling` | 自動 / 0.999 | SA 初期温度 / 冷却率 |
| `seed`(乱数) | 固定 12345 | 再現性のため固定（`rngSeed` で変更可） |

```js

optimize({
  poolCount,                 // プール数
  format,                    // 'DE' | 'SE' | 'RR' | ...（プール予選形式）
  ranking,                   // [uid, ...] シード順（先頭=seed1）

  recentMeta,                // 省略可: { key: {count,lastDate,lastDeltaDays,
                             //   lastTournament,lastNent} } レポートの表示用メタ
                             //   （日付/回数/最終対戦の大会名・規模）。スコアには使われない

```

**モード別デフォルト（`MODE_DEFAULTS`, ベンチ調整）**: `input.params` の明示値が最優先。
`hillclimb`: maxItersScale 1500 ／ `sa`: saCooling 0.999・maxItersScale 1000 ／
`multistart-hillclimb`: restarts 15・maxItersScale 1000 ／ `multistart-sa`(既定): restarts 15・saCooling 0.999・maxItersScale 1000。
未知の `mode`・空/負の `roundWeights`・負の `kInter`/`kIntra` 配列・負/非数の `maxSeedShift` は throw（無言の降格・恒等解を返さない）。
worker の多点スタートも restarts 未指定時は同じ `MODE_DEFAULTS` を使い、ベスト選択は
after.total 優先・同点なら order 罰則（元順位ズレ）が小さい方。
